## 用語

| 用語 | 意味 |
|---|---|
| となり | この作品。机の横に置いたスマホ（または PC の Web カメラ）と、それを動かすサーバの総称 |
| デバイス | 手元を撮って声を出す側。スマホのブラウザで `/device` を開いたもの。アプリは作らない |
| 学習者 | 紙のワークシートを解く人。想定は中学生。デモでは D が演じる |
| ワークシート | 自前で作る印刷用の問題用紙。シート ID（`WS-01` など）と 4 問を載せる。正答と典型ミスはサーバだけが知る |
| 動きスコア（motion） | ブラウザが 1 秒ごとに計算する、直前のフレームとの差の大きさ（0〜1）。映像はこの計算のためだけに使い、毎秒は送らない |
| 静止（still） | 動きスコアがしきい値を下回っている状態。考えているのか、詰まっているのか、席を立ったのかはこの時点では分からない |
| 詰まり（stuck） | 静止が `stuck_seconds`（既定 20 秒）続いた状態。ここで初めてフレームを 1 枚サーバへ送り、ヒントを作る |
| ヒント段階（H1・H2） | H1 問い返し（固定文）、H2 着眼点（GPT が答案を見て 1 箇所を指す）。1 回目の詰まりは H1、2 回目以降は H2。**どの段階でも答えは言わない**。H3 次の一手・H4 類題は Kaizen Sprint |
| 答え漏れ検査（leak check） | 生成したヒント文に、サーバが知っている正答の文字列が含まれていないかを機械的に調べる処理。含まれていれば捨てて固定ヒントに差し替える |
| 固定ヒント | ワークシートに人が書いておいた、問題ごと・段階ごとのヒント文。H1 は常にこれ。H2 は GPT が使えないときや答え漏れ検査に落ちたときの代わり |
| 声のトリガー（voice） | 学習者が「わからない」「わかんない」「ヒント」と言ったのをブラウザの音声認識で聞き取り、ボタンと同じヒント要求を送る。`trigger: voice`。ピッチでは使わない |
| 詰まりポイント（stuck_point） | ヒント生成時に GPT が付ける短いラベル（例「移項の符号」）。記録画面の集計に使う。映像の代わりに残すもの |
| 正誤チェック（check） | 学習者が「できた」を押したときだけ、最終答案を読んで正誤を判定する処理。自動では走らない |
| モード | `live`（本番。GPT を呼ぶ）／`scripted`（GPT を呼ばず、固定ヒントを順に再生。API 障害時の保険）／`mock`（フロントだけで動く） |

## Notion へのインポート手順

1. Notion で取り込み先のページを開く。
2. 右上の「…」→「インポート」→「Markdown & CSV」を選ぶ。
3. この `docs/` の `.md` ファイルを複数選択して取り込む（1 ファイルが 1 サブページになる）。
4. Mermaid の図は、取り込み後にコードブロックの言語を「Mermaid」にすると描画される（取り込み時に言語が落ちることがある）。
5. 表の中の `|` を含む文字列（API の `a|b` 表記）は崩れることがあるので、崩れていたら該当セルだけ手で直す。

## 文書の更新ルール

- 1 ファイル 1 テーマ。区切りは見出し階層で表し、水平線（`---`）は使わない。
- 何かを決めたら、まず上の「決定事項」に 1 行足し、該当ファイルを直す。
- docs に書かれていない設計判断（選択肢が 2 つ以上あったもの）は、実装より先に `docs/adr/` に ADR として書く（Hack Day 当日から。書き方は `docs/adr/README.md`）。
- 「要確認」と書いた項目は、確認できたら結果を書いて印を消す（12 の一覧にまとめてある）。
- 図は Mermaid のコードブロックで書く（GitHub と Notion の両方で描画される）。
